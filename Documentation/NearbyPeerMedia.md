# Nearby media transfer

Apple implementation base `a5d330cc38c5239d50731c11c482b281afbec5fb` supplies signed-in Nearby discovery. File downloads and eligible music and video playback in Music Home use the existing cache and the same authenticated API session. The origin's optional `Medias/PeerManifest` record authorizes a precisely identified public file. An unavailable catalog uses the existing server path. Standard artwork thumbnails and profile images continue through their existing caches.

The manifest binds the complete size, chunk geometry, whole-file SHA-256 and the packed SHA-256 table. Each piece from a neighbor or the origin must match the expected length and digest before storage. The partial cache can hold non-contiguous verified pieces and serve those pieces while a download is still in progress. The same manifest can authorize reuse and sharing of intact pieces from earlier SDK `.part` downloads. Publication into the regular cache uses an atomic replacement after whole-file verification. Peer-assisted playback uses the completed verified file. Media that follows the original direct HTTPS playback route retains its streaming behavior.

The existing Nearby service can announce `media=1` and the lowercase SHA-256 of its ephemeral TLS leaf certificate DER. Requests use the local Bonjour service endpoint and pin that certificate. If a peer announces a valid decimal `media-port`, the client uses that TCP port on the host resolved from the same Bonjour record. If the field is absent or invalid, the client uses the Bonjour SRV port. The piece wire request is the ASCII value `MZP1`, the 32-byte raw file SHA-256, a big-endian 32-bit chunk size and a big-endian 32-bit piece index. The response contains a big-endian length followed by that many bytes. A zero length means the peer lacks the piece. The LAN path carries piece requests and media bytes. Account authentication stays on the configured origin.

The app retains a bounded index of approved media references. It restores an entry by obtaining fresh origin approval for the signed-in account. Nearby shutdown closes active LAN connections. The partial store holds a bounded disk working set, supports files up to 8 GiB and verifies cached data before sharing.

## Validation

Apple uses Swift SDK revision `9c7f4621e276f07d48fb960ae44a202dc3b018a0`. The SDK's 35 tests cover 404 and authorization fallbacks, credential isolation for public storage and exact origin ranges. The Apple suite passed 66 tests in 11 suites, including both opt-in LAN tests. One test assembled and verified a file using two pieces from separate incomplete Bonjour TLS neighbors and two pieces from the test origin. The other used a separate native TCP/TLS listener announced through `media-port`. The transfer suite includes a sparse file checkpoint beyond 5 GiB and legacy cache fixtures for valid, mismatched, truncated and symlinked data. Independent TLS clients verified negotiation with the Apple listener over TLS 1.2 and TLS 1.3.

On the live network, the Swift client connected to the Windows NativeAOT fixture and obtained its exact 4,096-byte piece. Windows returned length zero for the next piece. These exchanges also passed through the revised Windows listener advertised by `media-port`. The Windows wire implementation uses the .NET SDK at `cfe641619116439f0387b6a8f63f96443e801860`. The public manifest endpoint was published in server revision `c85573a08ebb125a857b416bd227e88c4dd53f8a`. Live application transfers depend on the running backend and provisioned public manifests.
