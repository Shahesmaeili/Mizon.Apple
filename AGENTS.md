# Mizon Apple development requirements

Apple counterpart of [Mizon.Windows/AGENTS.md](https://github.com/Shahesmaeili/Mizon.Windows/blob/075cd99b240a7ed5b5a05a3d29dbe4daa02e9655/AGENTS.md) and its linked [shared workflow](https://github.com/Shahesmaeili/Mizon.Windows/blob/075cd99b240a7ed5b5a05a3d29dbe4daa02e9655/docs/ai/COLLABORATION.md) and [MCP guide](https://github.com/Shahesmaeili/Mizon.Windows/blob/075cd99b240a7ed5b5a05a3d29dbe4daa02e9655/Mcp/DEVELOPMENT.md). Applies to every contributor. The user's current instructions take precedence.

## Before editing

- Read this file, the Apple README and project structure, the latest relevant handoff and task notes, and recent commits. Inspect the actual Windows page, view model, resources and backend/SDK contract for behavior being ported. Compare with the reference revision. Verify the current Apple branch rather than inferring functionality from plans, screenshots or old handoffs.
- Fetch and inspect branch, status, HEAD and upstream divergence. Reuse the existing checkouts and relative project/package references. Do not duplicate source trees or rewrite local Xcode configuration as a shortcut.
- Follow the established naming, layering, localization, disposal and UI conventions. View models end in `ViewModel`. SwiftUI presentation belongs in `MizonAppleUI`, Apple application state and coordination in `MizonAppleCore`, and scene/target setup in `App`. Shared Swift transport, wire DTOs, operations and endpoint groups belong in `Mizon.API.Swift`. Backend business operations, routes and EF mappings remain in the server and database repositories. Use the same existing source of business rules on both clients.

## Swift, performance and responsive UI

- Use the latest Swift and Xcode toolchain supported by the project and dependencies. Use Swift 6 strict concurrency, structured tasks, explicit `Sendable` ownership and typed `Codable` contracts. The Apple counterpart to checking .NET NativeAOT is verifying relevant optimized native Swift builds and their supported architectures. Avoid reflection-based fallbacks, unbounded dynamic dispatch and broad warning suppression. Report Debug and optimized build checks accurately.
- Keep cold start, slow networks, scrolling, interaction, animation and repeated navigation fast. Use minimal payloads and decoded representations. Keep I/O and expensive work off the main actor, retain streaming and backpressure, and bound network work, polling, buffers and caches. Reuse the current media download/cache and playback owners. Cancel superseded work, prevent late responses from mutating dismissed UI, and release subscriptions, timers, streams, animations, media and native handles.
- Preserve accepted designs, controls, animations and functionality unless asked to change them. Use the Windows reference for behavior and dimensions and SwiftUI, Liquid Glass and Apple platform conventions for rendering. Preserve native keyboard, pointer and touch input, live Persian/English localization, RTL/LTR reading and layout, localized fonts, VoiceOver labels/announcements, visible focus and Reduce Motion.
- Verify responsive behavior at narrow/wide and short/tall window sizes and on supported iPhone layouts. Check dynamic sizing, focus and scrolling, plus loading, empty, error and disabled states. Instrument changed bottlenecks and report what was measured. Avoid claims based only on a successful build.
- Treat portrait, landscape left and landscape right as required iPhone layouts for every new or changed screen, sheet and header. Verify rotation and return to portrait with relevant menus, keyboard, scrolling or playback active. Let full-width backgrounds and header surfaces reach the display edges while keeping controls and readable content clear of the sensor housing, system indicators and home indicator. Preserve navigation, focus, scroll position and in-progress input when the device rotates.
- Preserve typed API/SDK compatibility, cancellation and bounded work through database, server, SDK and consumer. If the task requires changes outside Apple, keep type catalogs and code-first schema changes in their owning repositories, project only needed fields, follow existing bounded query and DbContext ownership patterns, and leave data backfills or live migrations to explicitly authorized tasks.

## Xbox controller input

- Every new or changed interactive page or feature must support Xbox controllers via Apple's GameController framework. Reuse the UI's actions, validation, focus and navigation. Use directional navigation, A for the focused action and B for back/cancel, with meaningful mappings for other controls. Leave system-reserved Xbox/Share actions to the OS.
- Provide predictable initial and restored focus, visible accessible focus, directional navigation and scrolling to focused controls. Handle adaptive/RTL layouts and changing lists. Avoid focus traps, decorative targets and actions on disabled, loading or unavailable controls. Constrain input to the active dialog/surface, restore focus on dismissal, keep default actions clear and let back dismiss the nearest appropriate surface.
- Where text is required, support a usable controller editing path using a supported system keyboard or explicit entry UI. Cover entry/exit, caret and selection as applicable. Preserve password masking, supported languages, accessible localized hints and Reduce Motion. Do not claim controller completion if required text cannot be entered.
- Consume input only from the active foreground window and page/dialog. Handle dead zones, directional stability, press edges, bounded repeats and switching between controllers and other input. Reset held/repeat state on ownership change, disconnect/reconnect, suspend/resume and close. Held buttons must not resubmit, dismiss a new dialog or activate its replacement. Stop inactive polling and release subscriptions and handles.
- Test input, focus/action eligibility, held/repeat/dead-zone behavior, connection changes, cancellation and lifecycle through the actual production paths using synthetic input. Report physical Xbox hardware, visual focus, dialog/text entry, VoiceOver and animation checks independently from automated tests. Extend coverage with each feature and record remaining gaps.

## MCP is part of feature development

- Every new or changed user-facing feature/page must expose appropriately scoped MCP read-state/actions and include meaningful MCP integration checks. Update existing contracts as behavior changes. Use the live SwiftUI model, navigation and business services, with UI work on the main actor and asynchronous I/O. Styling-only changes reuse existing MCP contracts/checks.
- Use Windows MCP capabilities as the parity reference: Welcome/Login/Registration, appearance, declared navigation, taskbar pinning and music home. For shell features, use the corresponding supported Apple capability, such as Dock integration on macOS, only where the platform permits it. Report implemented Apple coverage separately. Navigation scope does not expose a destination's business data/actions, and Windows coverage does not establish Apple coverage.
- Make `tools/list` side-effect free with typed input/output schemas, explicit tool names, descriptions, required/optional fields, enums and limits. Keep Swift `Codable` contracts and schemas synchronized. Register handlers explicitly, propagate cancellation, clean up sessions and use sanitized structured errors that distinguish permission, validation, unavailable page, cancellation and backend failures. Avoid automatic retry of mutations that may already have taken effect.
- The user grants access in Mizon. Default to denied, disclose new permission groups, and distinguish read, control and consequential submission. Authentication grants do not authorize music, appearance, settings or other domains. A Codex connection alone grants no app access. Discovery may list schemas before approval, while actual state and actions require their scopes.
- Restore persistent pairing only with the locally configured host's random proof and exact approved scopes. New domains need approval. Keep legacy clients without proof session-only. Global disable suspends access without discarding grants. Revocation removes the grant and cancels live sessions and work from older authorization generations, including for clients that are presently offline. Keep transport availability deadlines separate from UI handshake deadlines.
- Never let a tool or test grant itself access, change its scopes or bypass consent. Do not expose arbitrary reflection, shell, SQL, URL execution, unrestricted navigation or input injection. Keep passwords, tokens, cookies, pairing proofs and raw authentication payloads out of MCP state and logs.
- Test the real adapter or transport boundary and resulting app behavior, including relevant pending/denied/revoked, insufficient scope, stale or disconnected sessions, wrong proof, restore, storage failure, cancellation, errors and cleanup. Use synthetic inputs and test doubles for writes. Do not create real accounts or submit real forms simply to obtain a passing test. Headless MCP checks do not replace visual, animation or UI performance checks. Run Apple UI automation only when the user requests it and report unverified native or consent-dependent cases.

## Collaboration and delivery

- For concurrent work, agree on ownership and use separate Git worktrees, branches and build output directories. Use an integration owner for contracts spanning repos. Do not share a staging index, edit the same files simultaneously, or switch, reset or rebase a shared dirty checkout. Fetch incoming handoffs before depending on them. Markdown is durable context and Git coordinates revisions.
- Keep a scoped task note for cross-repository work with requirement, owner, task ID, base SHA, owned files, contract/dependency decisions, validation and remaining limits. Use the existing workflow task-note structure and record exact dependency commits. Coordinate contract/schema changes across Database, Server, SDK and client, and revalidate the combined result.
- After completing a task, review the diff, verify the changed behavior, and commit and push the intended scope to GitHub. Routine scoped commit/push is authorized by the standing workflow. A later explicit user instruction overrides it. Use explicit paths or hunks and preserve unrelated staged, unstaged and untracked work. A one-time authorization to publish all project source does not apply to future edits.
- Push coordinated changes in dependency order. Verify the remote SHA and report repository, branch, commit, checks and any unresolved work. Use a concrete English commit subject and a body describing changes, compatibility, validation and limits when useful. Do not create empty commits. Preserve work and report any failed publish or blocked validation.
- Integrate upstream changes without rewriting others' history. Inspect and resolve conflicts before declaring integration complete, and rerun the affected checks. Do not force-push, discard others' work or bypass branch protections.
- Keep tokens, secrets, certificates and private keys, consent stores, caches, logs, test accounts, local connection settings and generated builds out of commits. A source push is not authorization for production deployment, live migrations, real account changes or MCP approval. Use isolated test data and preserve user-owned running IDE and service sessions when checking code or documentation.
- Keep policy and implementation facts distinct. Keep linked upstream policy revisions traceable and update Apple handoffs when scope, contracts or coverage change. Report exact platforms, configurations, measured checks and limits. A plan, compile, screenshot or prior agent report cannot establish runtime, hardware, performance or consent-dependent results.
